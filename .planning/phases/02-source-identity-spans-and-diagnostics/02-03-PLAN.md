## Artifacts this phase produces (this plan)

- `diagnostic.hpp`: `DiagnosticSeverity { Error, Warning, Note }`; `RelatedSpan { SourceSpan span; std::string label; }`; `Diagnostic { DiagnosticSeverity severity; std::string message; std::optional<SourceSpan> primary; std::vector<RelatedSpan> related; }` in namespace `veyr`. Values own messages/labels; SourceSpans remain lightweight references resolved only with the originating manager.
- `diagnostic_engine.hpp/.cpp`: `DiagnosticEngine::emit(Diagnostic)` takes an owned value; `diagnostics() const -> std::span<const Diagnostic>` exposes insertion order; `has_errors() const -> bool` scans severity, independent of rendering. Returned collection views are valid only until the next emit or engine destruction, unlike manager-backed text views. No filtering, sorting, dedup, diagnostics clear/reset, global singleton, locking or output callback.
- `veyrcore` gains `src/diagnostics/diagnostic_engine.cpp`. New `diagnostic_tests` uses existing policy, veyrcore, GTest::gtest_main/GTest::gmock and PRE_TEST discovery. `tests/diagnostics/diagnostic_test.cpp` contains `Diagnostic.*` cases.
- No SourceManager/LLVM/driver ownership is embedded in the engine; validation of referenced spans happens in checked SourceManager/renderer operations. No new compiler driver success/exit logic is added in Phase 2; later clients must treat has_errors() as a failed compilation handoff.
